## 00:35 Q1 的真实根因

不是 `stopCapture` 掐输出——用坏文件里的时间戳把 `endRecording` 的算式重算了一遍，
问题在**暂停折叠时钟被减了两次**：

```
写进文件的末帧 PTS        = 68868579834 ns
endRecording 重算出的末帧  = -1829650506541 ns   ← 负 1829 秒
append 的 repeatedAtStop  = 68855457375 ns
```

`mediaTimeForSourceTime()` 会减去「此刻」的 `pausedAccumNs`。用户 00:03:44 恢复、
00:03:49 就按了结束，接收器侧的 pause 还开着，那 1898.5s 的暂停被第二次扣掉，
末帧 PTS 算成负数；末帧 PTS 又比重复帧晚 13ms，`AVAssetWriter` 直接拒绝写入，
`finishWriting` 失败，moov 永远写不出来（`NSCocoaErrorDomain 11800`）。

修法：
- 新增 `lastFrameMediaTime`：每帧写入时记下真正交给 writer 的 PTS，`endRecording`
  不再重算，杜绝二次扣减。
- 新增 `lastFrameFoldedHostNs` / `mediaTailNs`：尾部时长改在折叠后的 host 时钟上量；
  暂停中停止则 tail=0，不再凭空延长冻结帧。
- 折叠逻辑抽成 `src/capture/MediaClock.h`（纯函数），新增 `media-clock` 单测，
  **用坏文件的真实时间戳当夹具，并把旧表达式作为负向对照钉住**——
  测试里有一条断言专门验证旧公式会算出 68855457375。

## 01:10 Q6 长片导出被内核 OOM 杀掉

第一次跑全片合成（7480 帧）在 41% 处被杀，两次都是：

```
kernel: low swap: killing largest compressed process with pid 91711
        (jianku-compose) and size 82690 MB
```

RSS 涨到 **82 GB**，压进 8GB swap 后触发 low-swap killer。

根因是 `QProcess` 的写缓冲没有上限。`waitForBytesWritten()` 只在「缓冲区从非空第一次
被冲进管道」时有意义，之后立刻返回——循环里那句 `waitForBytesWritten` 根本挡不住 Qt
在父进程里堆积 **26.9 MB/帧** 的 BGRA。加上两个子进程的 stderr 从没被读过，管道写满后
还会反过来把 ffmpeg 卡死。

修法：用 `bytesToWrite() > 2 帧` 作为水位做真正的背压；全程持续 drain 两个子进程的
stderr（超时/中断时才有诊断信息可读）。

**实测：同样的全片合成 RSS 稳定在 284 MB，全程跑完。**

## 01:30–03:30 后半程（Q8–Q12）

### Q8 成片被 `-shortest` 裁短

全片合成 7480 帧，成片里只有 7470 帧，程序报 `EXIT=0`。两个原因叠在一起：
`-shortest` 把已经合成好的视频裁到音轨长度（系统声音比视频时间轴短），
而合成器只信自己写进去的帧数、从不回读成片。去掉 `-shortest`，并加
ffprobe `-count_packets` 回读校验。全片重跑：7480 写入 / 7480 回读，
`ffmpeg -f null -` 完整解码无错。

### Q11 窗口与区域来源

抽了与平台无关的 `CaptureSource`（描述 + 几何解析），三种来源共用一条管线。
`PointerEventRecorder` 不再自己推包围盒，改由调用方传入实际录制矩形——否则

**两个靠独立探针实测出来的结论，方向相反：**
- **窗口阴影是真的坑。** 含阴影时帧尺寸仍是 `window.frame × scale`，但内容从

这两个结论的差别完全是靠对照做出来的，不是靠看得更仔细。

### Q12 动态模糊

上次那套实时 GLSL 按用户要求整体删过（放大闪烁、平移花屏）。这次换路：合成器
已经是逐帧离线渲染，模糊就做成对「上一帧姿态 → 这一帧姿态」的纯函数，没有
GPU 状态、没有帧间残留。

**位移上限。** 静态笔记的两个阈值（1 与 0.01）差一百倍，说明强度乘子的单位

### Q13–Q14 画布包装三处各写一遍

「快捷截图只认纯色背景」是这一轮里唯一一个用户打开就能看见的差异：设置里选了
渐变或内置背景，预览是渐变，截出来的 PNG 是一块纯色。留白还更隐蔽——预览按画布
宽高各取百分比，合成器按短边取，同一个「留白 10%」在两边不一样宽。

抽 `CanvasRenderer` 时把这两件事一起解决，并且是**先有测试再相信**：`canvas-renderer`
里断言两种留白解法的**比例**必须一致（绝对值本来就该不同，比例不同才是 bug）、
不同画布比例下来源不拉伸、渐变方向与预览一致、圆角/内框/阴影真的落到像素上。

顺带发现并修掉一处镜像：预览的渐变走 QML 顺时针旋转，合成器走 `QLinearGradient`
的数学角度，同一个 135° 在两边是反的。测试把约定钉死了。

### Q15 用参考工程验证动态模糊默认值

本机有 6 个参考软件已保存的工程，只读看了它们的 manifest。四个 motionBlur 分项
强度全部是 1，跨 11 天一致——这比安装包里的静态基础对象强一档，因为它记录的是
「这一次录制实际用了什么」。同时确认留白与圆角是用户值而非默认值，所以不能拿
任何一个工程当新工程默认。

一个诚实的负面结论：**圆角的单位定不下来**。工程里是无单位整数 12，导出时才有
像素尺寸，按画布/来源点/来源像素三种解释差一倍。官方文档说整屏来源取 0，但本机
6 个工程全是整屏来源、圆角却是 9/0/21/14/7/12。没有参考导出帧就不能判断，已记为
待验证项，当前按画布像素处理并写明理由。

### Q16–Q17 非破坏性编辑时间线

编辑器 UI 的形态可以等，但**输出时钟**不能等：画面、指针、镜头、音频都要从同一个
映射取时间，先做 UI 再补映射，剪辑点两侧的点击就会落在错的地方且很难查。

做法是一条规则推到底：输出时间线是若干片段的拼接，每段把
`sourceEnd-sourceStart` 的素材以 speed 播成 `(sourceEnd-sourceStart)/speed` 的输出
时长。由此得到两个不变量——**连续**与**严格单调**——它们就是 `edit-timeline` 测试
贯穿全文件的属性检查（往返闭合 + 单调性），而不是抽查几个点。

`TimelineController` 只加 UI 需要的东西，算术仍只有一份。两个出错了用户会丢工作
的行为钉在测试里：失败的操作什么都不改也不进历史；成功才记一步，撤销后再编辑
清掉重做分支。

真实 124.66s 工程上逐帧验证拼接是否正确：删掉 0.5–1.5s 后，输出第 29 帧与原片
第 29 帧相符 100%，输出第 30 帧（剪辑点）与原片第 90 帧相符 99.97%，第 35 帧与
原片第 95 帧相符 99.98%。差异来自编码，不是映射。

`_exit(0)` 模拟被杀。结果很干脆：**换容器没用**（两种容器的普通写法都报
`moov atom not found`），**分片写入解决**（两种容器的分片写法都能播）。

但只修视频等于没修：探针又测出 `QFile` 逐行写在被杀后会留下 **0 字节**
（Qt 把数据留在用户态缓冲），而 `loadProject` 拒绝空帧时间线。
再测周期 flush：十次 flush 只要 **0.2 ms**，丢失量正好是一个 flush 周期。
所以取 60 帧（约 1 秒），与视频分片间隔对齐。

这一轮没有任何一步是推断出来的——四个探针、每个都跑出可比较的数字。
那个坏文件救不回来（mdat 里只有 371KB 能解析），也没有动它。

### Q19 把算术留在能测的地方

时间线界面最容易犯的错是把几何算在 QML 里：那样「剪辑点在哪」就有两个答案。
所以先抽出 `TimelineGeometry` 纯函数并单测（比值往返闭合、帧吸附在尾部不越界、
平局取更早的切点、刻度必带末尾、离谱步长返回空而不是把 UI 撑死），
QML 只负责摆放。

`timeline-strip` 这个测试是这一轮最值的一点：它把 **QML 告警当失败**。
QML 绑定坏了不会加载失败，只打一行 warning 然后渲染成空白——这正是
「时间线安静地什么都不显示」的成因，而普通启动根本不会加载到那条分支
（没有工程时整条隐藏）。搭它的过程本身也踩了三个坑，都写进了注释。

`ctest` 15/15，本轮 2 个提交，未 push。

## 第四轮（05:05–05:35）：界面交互、音量缺陷，与一次设置项审计

### Q20 拖拽

时间线补上首尾裁剪把手与变速按钮。变速只作用于**播放头所在的片段**——剪辑后
影响旁边的段会让用户没指的内容被静默改掉。这里有个容易混的地方：所有操作都是
**输出时间**，素材时钟已经被前面的剪辑平移过（裁头 2 秒后「裁到 7 秒」得到的是
素材 9 秒），测试专门钉住了这一条。

也把上一轮那个 QML 测试的**真实覆盖**量了出来：故意改成读不存在的属性，
Qt 6.11 **不报警**，只求值成 undefined。所以那个测试保护的是「确实被求值到的
绑定」，不是全部。这条限制写进了测试文件开头——一个被高估的测试比没有测试更危险。

### Q21 一个真正接错线的缺陷

设置页的两个音量滑块，工程里也存着值，但**没有任何代码读**：`ComposeOptions`
有字段而始终是 1.0。实测确认修好了：麦克风 0.25 让 mean_volume 降了 12.1 dB，
与 0.25 倍的理论值 12.04 dB 相符。

顺带查了同样没人读的 `mouseClickSpring`——但这次**没有**接上。已定位的参考
调用链写着 zoomer-and-fader 用的是它自己的弹簧（300/30/0.3），就是引擎现在跑的
那个。接上它看起来像在修 bug，实际是在制造一个与证据矛盾的改动。改成加断言把
「故意忽略」钉住。

### Q22 审计，以及一个必须说清的区分

把 72 个设置键逐个搜引用方。21 个只被设置界面引用，但其中 20 个是**尚未实现的
功能**（摄像头、字幕、快捷键显示、背景音乐、点击音效），队列里本来就列为
「明确未做」——它们是缺失的功能，不是缺陷。真正的「写了没人读」只有 Q21 那一个
（外加四个已存储未实现的字段）。

这个区分值得单独写下来：把「还没做的功能」说成「bug」会让待办清单看起来比
实际严重，反过来把「本该生效却写死」混进功能列表里则会漏掉真缺陷。
