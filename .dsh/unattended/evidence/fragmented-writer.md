# 分片写入：写到一半被杀的文件到底丢多少（探针实测）

日期：2026-10-04。目的：确定「录制中途进程被杀」这个真实故障该怎么修，
以及在动手前先量清楚每种写法的实际后果。

## 起因

本机 `~/Movies/Jianku Screen/Jianku Screen 2026-10-03 23-27-15-049.jianku`
是一个真实损坏的录制：28.3 MB 的 `raw.mp4`，`state=failed`，
`error="The operation could not be completed"`，录制了 68.9 秒、3938 帧。

对它做结构分析：

```
ftyp(28) wide(8) mdat(声明大小 0 = 到文件尾)
moov 0 次   moof 0 次   mfra 0 次   sidx 0 次
```

索引（`moov`）是 `finishWriting` 时才写的，进程没走到那一步，所以整个文件
**一个解码器都打不开**。这不是「丢了最后几帧」，是 28 MB 全丢。

进一步看 `mdat` 内容：前 564 字节是 `21 00 03 40 68 1c` 的重复填充，
之后有一段可解析的 AVCC 样本流（1 个 SPS + 1 个 SEI + 28 个 P 帧，
共约 371 KB），再往后就再也没有可解析的 NAL 结构了。也就是说即使手工重建索引，
能救回的也只是第一帧附近的内容。

顺带排除了两个猜测：
- **不是暂停折叠算错**（那是 `bee294b` 修的问题，症状是 PTS 为负）。
- **不是磁盘满**（文件大小、时间戳、其余 5 个工程都正常）。

## 两种写法的对照实验

探针 `probe.mm`：用 AVAssetWriter 写 90 帧 640×360 的合成画面，
写到最后一帧后**不调用 `finishWriting` 直接 `_exit(0)`**，模拟进程被杀。

| 写法 | 容器 | 被杀后的结果 |
|---|---|---|
| 普通 | MPEG-4 (`.mp4`) | `moov atom not found`，**完全打不开** |
| 普通 | QuickTime (`.mov`) | `moov atom not found`，**完全打不开** |
| `movieFragmentInterval = 1s` | MPEG-4 (`.mp4`) | 可播，时长 2.000 s |
| `movieFragmentInterval = 1s` | QuickTime (`.mov`) | 可播，时长 2.000 s |

结论一：**换容器没用**。`.mov` 和 `.mp4` 的传统写法都要 `moov` 才能读，
容器选择不影响这件事。

结论二：**分片写入直接解决**。分片模式下每片自带 `moof`，不需要文件尾的索引；
被杀时丢掉的是最后一个未完成的分片，最多一秒。

另一个探针 `probe2.mm` 确认正常结束时不会有副作用：设了
`movieFragmentInterval` 后调用 `finishWriting`，状态仍是 `completed`，
时长正确（2.000 s），完整解码无错。所以这是一个**只有好处、没有代价**的改动
（除了一点分片头部开销）。

## 本仓库的改动

`src/mac/MacCapture.mm` 的 `beginRecordingAtURL:` 加一行
`newWriter.movieFragmentInterval = CMTimeMake(1, 1);`。

## 与合成器的兼容性

合成器读源视频有两条路，两条都在分片文件上验过：

- ffmpeg 解码：`ffmpeg -v error -i frag.mp4 -f null -` → 无错误输出，退出码 0。
- 帧数回读（`ProjectCompositor` 校验成片用的方式）：
  `ffprobe -count_packets` → 60 个包，时长 2.000 s，与普通写法一致。

## 边界与遗留

- 分片间隔 1 秒是一个**选择**：它决定最坏情况下丢多少（约 1 秒），
  代价是每秒一个 `moof` 头。没有和参考的落盘结构做逐字节对照，
  参考用的是 `.m4s` 分片 + `.m3u8` 索引（见 `research/参考工程实测值.md`），
  那是它自己的分片方案，本仓库不需要照抄才能达到同样的可靠性。
- 本次没有改「录制中途被杀时 `project.json` 的状态」：现在崩溃留下的工程仍是
  `state=failed`，但 `raw.mp4` 已经可读了。要不要在启动时扫描并修复这类工程，
  留给后续（需要用户先定行为：自动修复、还是提示用户）。
- 修复不了那个已经损坏的文件：它的 `mdat` 里只有约 371 KB 可解析，
  恢复不出 68.9 秒的画面。**没有动它**（授权边界：`~/Movies` 只读）。

## 补充：帧时间线也必须周期性落盘（探针实测）

分片只救视频。`video-frames.jsonl` 是 Qt 的 `QFile` 逐行 `write`，只在结束时
`flush()`，而 **Qt 会把这些 write 全部留在用户态缓冲里**——实测写 100 行后不 flush
直接 `_exit(0)`，文件里是 **0 行 0 字节**。所以只修视频的话，崩溃留下的工程仍然
加载不了（`loadProject` 会因为帧时间线为空直接拒绝）。

又测了周期 flush 的代价与效果：

| 探针 | 行为 | 被杀后文件内容 |
|---|---|---|
| 写 100 行，每 10 行 flush | 10 次 flush，耗时 0.2 ms | **100 行全在** |
| 写 95 行，最后一次 flush 在第 89 行 | — | **90 行**，丢最后 5 行 |

结论：flush 的代价可忽略（十次 0.2 ms），而丢失量正好是最后一个 flush 周期。
所以取 `kTimelineFlushEveryFrames = 60`（60 fps 下约 1 秒），与视频分片间隔一致，
两边丢的范围对齐，不会出现「视频有、帧时间没有」的错位。

## 补充：合成器确实能吃下分片文件

用 ffmpeg 把真实录制的前 6.9 秒重封装成 `frag_keyframe+empty_moov+default_base_moof`，
结构是 `moof×3 + mdat×3`（与 AVAssetWriter 的 `moov` 在前的分片布局不同，
但都是合法的分片 mp4）：

- `ffprobe` 读到时长 6.900 s、360 个视频包。
- 用探针产出的「被杀的分片文件」造了一个最小工程跑完整合成：
  60 帧输入 → 60 帧输出、回读 60、时长 2.000 s、342.9 帧/秒。
  也就是说 `raw.mp4` 直接来自一个被杀进程的分片文件时，导出链路是通的。

## 修复不了的那个文件（结论）

对 `Jianku Screen 2026-10-03 23-27-15-049.jianku` 继续做了结构分析：
顶层只有 `ftyp(28) wide(8) mdat(声明大小 0)`，`moof`/`moov`/`mfra`/`sidx` 全是 0 次。
`mdat` 里前 564 字节是 `21000340681c` 的重复填充，之后有一段可解析的 AVCC 样本流
（1 个 SPS + 1 个 SEI + 28 个 P 帧，约 371 KB），再往后按任何对齐都解不出 NAL 结构。

**所以那 68.9 秒救不回来**——能解析出来的只有开头约 371 KB。**没有动那个文件**
（授权边界：`~/Movies` 只读）。
