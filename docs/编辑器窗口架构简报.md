面向实现工程师。目标：把编辑器从主窗口里搬出来，做成**独立窗口 + 可拖拽标签页**，并给出可落地的 Qt 6 方案。

## Screen Studio 编辑器的实际结构

### 窗口模型

- ✅ 录制结束后**编辑器是一个独立窗口**：「After you have finished recording, the editor window will appear, allowing you to edit your recording.」——[Starting & Finishing the recording](https://screen.studio/guide/starting-finishing-the-recording)
- ✅ 编辑器还有别的入口：录制结束后的 Quick Share 组件上的 **Edit**（[Quick share widget](https://screen.studio/guide/quick-share-widget-)）；菜单栏 `File → Open recent` / `Show previous projects`（[Saving your project](https://screen.studio/guide/saving-your-project)）。
- ✅ 导出是**独立窗口**，不是嵌在编辑器里的对话框：导出后「you will see the export progress window」（[Exporting the video](https://screen.studio/guide/exporting-the-video)）；更新日志 3.5.2 有一条「File save modal is sticked to the export window」（[Changelog](https://screen.studio/changelog)）。
- ✅ 存在**多窗口**能力：更新日志修复过「window resizing issue when there are multiple windows from the same parent」，并新增过「New system for saving window positions」（[Changelog](https://screen.studio/changelog)）。
- ✅ 本机 `/Applications/Screen Studio.app`（版本 **3.4.4-3794**，Developer ID `Adam Pietrasiak (SXF593CX2N)`，与 3.7.5 同一签名主体）的 `Info.plist` 声明了 `CFBundleDocumentTypes`，`.screenstudio` 与 `.screenstudiopreset` 均带 `LSTypeIsPackage = true`。→ 工程在 Finder 里是**单个文档包**，双击可交给 app 打开。
- ✅ 本机 3.4.4 的 `app.asar` 主进程里有通用的子窗口机制：`ChildWindowManagerProvider`、`window.updateChildWindow`、`window.focusChildWindow`、`closeChildWindow`、`CommandMenu__UIWindowDragger`（用该包自带的字符串解码器还原，见「方法说明」）。菜单模板里有一个 `Window` 菜单，含 `close` 与 `windowMenu` 两个 role。
- ❓ **我没有找到任何证据表明 Screen Studio 有标签页。** 它是「一个窗口 = 一个工程」，多窗口并存。**标签、标签拖动重排、拖出成窗都是我们要自己加的能力，不是复刻对象**，验收标准需要自己定。
- ⚠️ 上面 ChildWindow 的定位是**静态推断**：我没有运行 3.4.4、没有抓窗口层级，因此不能断言它就是编辑器窗口系统。
- ⚠️ 本机装的是 **3.4.4**，官网指南描述的是当前版（4.0 时期），`research/evidence/` 里的是 **3.7.5**。三套证据版本不同，交叉引用时要看版本号。

### 时间线的数据模型：**多轨**

- ✅ 不是单条胶片，而是**命名轨**：`Zoom track`（紫色块）、切片/剪辑轨（黄色）、`Layouts timeline`（摄像头布局）、快捷键轨、背景音乐/波形轨。
- ✅ 官方指南原文：「Each zoom is reflected on your `Zoom timeline` in the editor and is presented as **purple blocks**」（[Adding & Editing zooms](https://screen.studio/guide/adding-editing-zooms)）；「Your **Zoom track**」（字符串资源）；摄像头是「new **Layouts timeline**」（[Dynamic camera layouts](https://screen.studio/guide/dynamic-camera-layouts-)）。
- ✅ 更新日志里的轨道行为细节，直接说明了交互模型：「Always keep at least one track active」「Keep zoom track active if there are no zooms」「Properly hide resize controls for non-slice tracks」「Better waveform visibility on timeline」「Fixed timeline glitch with dragging one slice over another one」「Last zoom/camera layout on timeline now has the correct styles」（[Changelog](https://screen.studio/changelog)）。

### 缩放区间（zoom segment）的编辑交互

- ✅ **创建**：在 zoom 轨上想要的时刻点一下即新建（「simply click on the zoom timeline at the desired location」）。
- ✅ **改长度**：拖区间两端（「drag each zoom edge and adjust its length」）。
- ✅ **选中后开设置面板**：设置栏出现，可设 zoom level、`Auto`（跟点击）/`Manual`（自选区域）、`Instant Animation`。
- ✅ **删除**：右键 → `Disable` 或 `Remove`（Disable 保留区间但关掉效果）。
- ✅ **手动 zoom = 一个紫点**：预览上出现「a **purple dot** in the middle」，拖它选区域；手动取景器显示百分比且「snaps to 50% from ±1%」。
- ✅ 更新日志还有：复制/粘贴 zoom 区间与切片设置（2.26.0）、多选 zoom 区间批量操作（3.x）、「Removed glide options from the UI」。
- 来源：[Adding & Editing zooms](https://screen.studio/guide/adding-editing-zooms)、[Manual Zoom](https://screen.studio/guide/manual-zoom)、[Instant Zoom](https://screen.studio/guide/instant-zoom)、[Changelog](https://screen.studio/changelog)。

### 剪辑交互

- ✅ 剪刀/切分工具由 **按住 ⌥** 激活（不是切换开关）；`C` 在播放头处切开；`X` 是 ripple delete（删到上一个切点）；右键 → `Remove` / `Set speed` / `Set volume`；拖片段边缘裁头尾；每次裁剪在时间线上显示为一个**带剪刀图标的黄色气泡，点它撤销这次裁剪**。
- ✅ 时间线缩放：剪刀图标旁有滑杆；**⌘+滚轮**缩放；触控板捏合缩放；滚轮平移；播放中也能滚；缩放以播放头或可见区中心为锚点；「When removing slices, undoing, redoing - it will adjust playhead to show exact same moment of the source video」。
- ✅ 「Reduced minimum clip time to 100ms」「Increased minimum zoom duration to 1s」——最小片段长度是有具体数值的。
- 来源：[Trimming](https://screen.studio/guide/trimming)、[Speeding up the video](https://screen.studio/guide/speeding-up-the-video)、[Set Volume](https://screen.studio/guide/set-volume)、[Changelog](https://screen.studio/changelog)。

### 导出流程

- ✅ 点右上角 `Export` → 弹**导出设置**（GIF / MP4、frame rate、output size、quality）→ `Export to File` 或 `Copy to Clipboard` → **导出进度窗口**（ⓘ 可看完整输出路径）。
- ✅ 一份 4.0 的说明值得照抄：「compression level 不影响导出耗时；影响耗时的是 FPS、分辨率和格式」；GIF 比 MP4 慢得多，不建议超过 1 分钟。
- 来源：[Exporting the video](https://screen.studio/guide/exporting-the-video)、[Explanation of export settings](https://screen.studio/guide/explanation-of-export-settings)。

## OpenScreen 的编辑器架构

仓库：[siddharthvaddem/openscreen](https://github.com/siddharthvaddem/openscreen)（39.9k stars，TypeScript，Electron 41 + React 18 + Vite，版本 1.5.0）。我读的是 `f57e36e25448b5af6c7b1b271066fe5beb9b8a49`（浅克隆，2026-06-16）。

**按用户要求，我完全没有阅读它的动画/缓动实现**（`videoPlayback/zoomSpring.ts`、`zoomTransform.ts`、`motionSmoothing.ts`、`cursorRenderer.ts`、`zoomRegionUtils.ts` 等只列了文件名，未打开）。下面只谈窗口/工程/时间线/撤销/导出的外壳架构。

### 多窗口：**一份前端产物，多个窗口，用 query 参数选角色**

[`electron/windows.ts`](https://github.com/siddharthvaddem/openscreen/blob/f57e36e25448b5af6c7b1b271066fe5beb9b8a49/electron/windows.ts) 里四个工厂：

- `createEditorWindow()`：1200×800，min 800×600，macOS `titleBarStyle: "hiddenInset"` + `trafficLightPosition {x:12,y:12}`，深色 `backgroundColor`，`show:false` + `ready-to-show` 再 show（避免白闪），随后 `win.maximize()`。
- `createHudOverlayWindow()`（透明无边框悬浮条）、`createSourceSelectorWindow()`（选源）、`createCountdownOverlayWindow()`（倒计时）。

四个窗口**加载同一份 renderer**，只差 URL 查询参数：

```ts
win.loadURL(VITE_DEV_SERVER_URL + "?windowType=editor");
// 或 win.loadFile(RENDERER_DIST + "/index.html", { query: { windowType: "editor" } });
```

[`src/App.tsx`](https://github.com/siddharthvaddem/openscreen/blob/f57e36e25448b5af6c7b1b271066fe5beb9b8a49/src/App.tsx) 就是按这个参数 switch 渲染不同的根组件。

> **这是最值得移植的一条思路**：入口只有一份，窗口按角色参数实例化。映射到 Qt 就是「一个 `QQmlEngine`，多个 `Window`，用创建参数区分主窗口 / 编辑器窗口 / 悬浮控条」。

### 撤销/重做

[`useEditorHistory.ts`](https://github.com/siddharthvaddem/openscreen/blob/f57e36e25448b5af6c7b1b271066fe5beb9b8a49/src/hooks/useEditorHistory.ts)：`{past, present, future}` 三段式，`MAX_HISTORY = 80`，**整状态快照**（不是命令模式）。两个关键细节值得抄：

1. `pushState()`（离散操作）与 `updateState()`+`commitState()`（连续手势，比如拖滑杆）分开：手势期间 `dirtyRef` 让**第一次更新**成为检查点，后续更新只改 present，`commitState()` 收尾。这样一个拖拽只产生一步撤销。
2. **选中态刻意不进入撤销状态**：「Selection IDs are excluded, since undoing a selection change would feel surprising.」

### 打开 / 加载

IPC：`load-project-file`（弹对话框）、`load-project-file-from-path`（拖放）、`load-current-project-file`（启动时）。启动时 `VideoEditor` 依次尝试 ① 恢复上次工程 ② 取当前录制 session ③ 取当前视频路径，都没有就渲染 `EditorEmptyState`。

拖放**只在空状态组件里实现**（[`EditorEmptyState.tsx`](https://github.com/siddharthvaddem/openscreen/blob/f57e36e25448b5af6c7b1b271066fe5beb9b8a49/src/components/video-editor/EditorEmptyState.tsx)）：HTML5 `onDragOver/onDragLeave/onDrop`，过滤 `.openscreen`，用 `webUtils.getPathForFile()` 拿路径（`File.path` 在 Electron 32+ 被移除）。没有打开态下的拖放。

### 明确没有的东西（对我们的设计很重要）

- ❌ **没有标签页**，没有标签栏，没有拖出成窗，没有多工程共存。`createEditorWindowWrapper()` 是"关掉旧窗口、建一个新窗口"，`currentProjectPath` 是主进程里的**单个**变量。
- ❌ 主进程没有工程注册表；打开新工程就是替换当前那个。

### 未保存关闭

渲染进程上报 `set-has-unsaved-changes`；主进程拦 `close` 事件，`preventDefault()` 后给渲染进程发 `request-close-confirm`，渲染进程回 `save|discard|cancel`；选 save 还要再走一轮 `request-save-before-close` → `save-before-close-done`。**这套往返协议在 Qt 里不需要**——Qt 有原生的 `closeEvent` + `MessageDialog`。

### 导出

渲染进程侧 `src/lib/exporter/`（`VideoExporter` / `GifExporter`），`ExportDialog.tsx` 负责进度/取消/导出完成 2 秒后自动关闭；主进程只暴露 `pick-export-save-path` + `write-export-to-path`。设置栏底部那个整宽绿色按钮就是导出入口。

## Qt 6 实现路径

### 3.1 一个引擎，多个窗口

- ✅ 引擎析构会连带销毁它加载的全部 QML 对象：「Destroys the `QQmlApplicationEngine` **and all QML objects it loaded**.」——[QQmlApplicationEngine](https://doc.qt.io/qt-6/qqmlapplicationengine.html)。所以**不要每个窗口建一个引擎**：本项目的 `cursor://` 图片提供器、`qmlRegisterType<VideoSurface>`、以及全部 `setContextProperty` 都挂在唯一那个引擎上，第二个引擎什么也看不到。
- ✅ 根上下文天然对引擎创建的所有对象可见：「Data that should be available to all QML component instances instantiated by the engine should be put in the root context.」——[QQmlEngine::rootContext()](https://doc.qt.io/qt-6/qqmlengine.html#rootContext)。现有的 11 处 `setContextProperty` 不需要为多窗口改动。
- ✅ 但根上下文有代价，官方明确劝退：「Such data is **invisible to any tooling**, including the Qt Quick Compiler」，而且「Setting the context object or adding new context properties **after** an object has been created in that context is an expensive operation (essentially forcing all bindings to re-evaluate)」——[QQmlContext](https://doc.qt.io/qt-6/qqmlcontext.html)。→ **每工程的状态不要走根上下文**，要在创建标签页内容时注入（见 3.2 与第 4 节）。
- ✅ 同一个 `QQmlComponent` 可以反复 `create()` / `createWithInitialProperties(initialProperties, context)` 造出 N 个实例，这是官方的用法示例——[QQmlComponent](https://doc.qt.io/qt-6/qqmlcomponent.html#createWithInitialProperties)。`setInitialProperties()` 是给已创建对象补初始属性的对应 API。
- ✅ **本机探针实测**：一个 `QQmlEngine` + 一个 `Item` 根，用 `Component.createObject(null)` 造出两个 `Window`，各自有 `contentItem()`，两端内容独立渲染、绑定各自求值。多窗口共用一个引擎在 6.11.2 上工作正常。

### 3.2 跨窗口搬运一个活着的 `QQuickItem`（本简报的核心结论）

**这是整个标签页方案的风险点，我做了实测。** ✅ 结论：**在 Qt 6.11.2 上，一个活着的 `QQuickItem` 可以在两个不同的 `QQuickWindow` 之间来回搬运，绑定继续求值，item 不重建、不销毁。**

实测矩阵：

| 操作 | `item->window()` | `parentItem()` | `isVisible()` | 绑定(`tick`) | item 存活 |
|---|---|---|---|---|---|
| `setParentItem(hostA)`（窗口 A 内） | A | hostA | true | 递增 | ✅ |
| `setParentItem(hostB)`（**另一个窗口**） | **B** | hostB | true | 递增 | ✅ |
| `setParentItem(nullptr)` | `nullptr` | `nullptr` | **false** | 递增 | ✅ 未销毁 |
| 从 null 再挂回 hostA | A | hostA | true | 递增 | ✅ |
| QObject 父 = 窗口，窗口 close + 事件循环 | 已销毁 | — | — | — | ❌ **被销毁**（`QPointer` 证实） |
| QObject 父 = 根 Item，窗口 close | `nullptr` | 自动置空 | false | 继续递增 | ✅ 可再挂到别的窗口 |

文档依据：

- ✅ `Item.parent`「holds the **visual parent** of the item」，并明确视觉父与 `QObject` 父是两回事——[QQuickItem](https://doc.qt.io/qt-6/qquickitem.html#parent-prop)。
- ✅ 「if an item's `parent` property value is `null`, the item **will not be rendered** in the scene」——[Concepts - Visual Parent in Qt Quick](https://doc.qt.io/qt-6/qtquick-visualcanvas-visualparent.html)。注意：是"不渲染"，**不是"销毁"**。
- ✅ `QQuickWindow::contentItem`「the **invisible root item** of the scene. … To add items to this window, **reparent the items to the contentItem** or to an existing item in the scene.」——[QQuickWindow](https://doc.qt.io/qt-6/qquickwindow.html#contentItem-prop)。这是 C++ 侧往新窗口塞内容的官方途径。
- ✅ `QQuickItem::window()` / `windowChanged(QQuickWindow*)` 是搬运时该监听的接口——[QQuickItem](https://doc.qt.io/qt-6/qquickitem.html#window-prop)。

**三个必须记住的坑（都是实测踩到的）：**

1. **QML 里没有 `setParentItem()`。** 用的属性名是 `parent`：QML 写 `item.parent = hostItem`，C++ 写 `item->setParentItem(hostItem)`。我第一次调用 `c.setParentItem(host)` 得到的是 `TypeError: Property 'setParentItem' ... is not a function`。
2. **QObject 父决定生死，视觉父只决定画在哪。** 在 QML 里把标签内容声明在 `Window { Item { MyTab {} } }` 之下，它的 QObject 父就是那个窗口，窗口一关 item 就没了（实测 ❌）。所以：**标签内容的 QObject 父必须是会话对象（比窗口活得久），只有 `parentItem` 在窗口之间搬。**
3. **不要用 QML 嵌套的 `Window` 作为独立编辑器窗口。** 文档：「A Window can be declared **inside an Item or inside another Window**, in which case the inner Window will automatically become **"transient for"** the outer Window」——[Window QML Type](https://doc.qt.io/qt-6/qml-qtquick-window.html)。实测：根是 `Item` 时两个 `ApplicationWindow` 起来是 `visible:false`（offscreen 后端下尤其明显），根是单个 `ApplicationWindow` 时正常可见。要独立窗口，就在 C++ 里 `new QQuickWindow` 并把 QML 内容挂进 `contentItem()`，或者 `createObject(null)` 后显式 `setTransientParent(nullptr)`。

**给撕裂标签（tear-out）的建议**：保留一份**只搬视觉父、永不重建**的标签内容实例。这是唯一能保住视频播放位置、缩放动画相位、滚动位置的方案；重建内容会立刻丢掉这些。开工第一步应该把附录 A 的探针在**真机**上再跑一遍（我的探针跑在 offscreen 后端）。

### 3.3 Qt 开箱即用的 vs 必须手写的

#### 文件/文件夹选择器 ✅ 开箱即用

- `import QtQuick.Dialogs` → `FileDialog`（`fileMode`、`nameFilters`、`selectedFile`/`selectedFiles`、`currentFolder`）、`FolderDialog`（`selectedFolder`、`currentFolder`、`acceptLabel`/`rejectLabel`、`options`）、`MessageDialog`。macOS 上是**原生**实现——[FolderDialog](https://doc.qt.io/qt-6/qml-qtquick-dialogs-folderdialog.html)、[FileDialog](https://doc.qt.io/qt-6/qml-qtquick-dialogs-filedialog.html)。
- ✅ 多窗口下**必须显式设置 `parentWindow`**：`Dialog` 基类文档说「Unless explicitly set, the window is automatically resolved by **iterating the QML parent objects** until a `Window`…」——[Dialog](https://doc.qt.io/qt-6/qml-qtquick-dialogs-dialog.html)。在可复用组件里靠自动解析，会挂到错误的窗口上。默认 `modality: Qt.WindowModal`，默认 `flags: Qt.Dialog`。
- `.jianku` 是**目录**：用 `FolderDialog` 选目录，或者用 `FileDialog` 定位到父目录 + 自己渲染工程列表（`RecentProjects::list()` 已经能做这件事）。不要用 `FileDialog` 直接选包。
- ⚠️ 老模块 `Qt.labs.platform` 也有 `MenuBar`/`Menu`/`MenuItem`，文档明确警告「Types in Qt.labs modules are **not guaranteed to remain compatible** in future versions」——[Qt Labs Platform MenuBar](https://doc.qt.io/qt-6/qml-qt-labs-platform-menubar.html)。新代码用 `QtQuick.Controls`。

#### 从 Finder 拖入 ✅ 开箱即用

- `DropArea { onDropped: (drop) => … }`，`drop` 是 `DragEvent`（不可创建类型）。
- ✅ `DragEvent` 的属性/方法：`urls: urllist`、`hasUrls`、`keys`、`source`、`text`/`html`/`colorData`、`formats`、`proposedAction`、`supportedActions`、`x`/`y`、`accept()`、`accept(action)`、`acceptProposedAction()`、`getDataAsString(format)`、`getDataAsArrayBuffer(format)`——[DragEvent](https://doc.qt.io/qt-6/qml-qtquick-dragevent.html)。
- ⚠️ 从 Finder 拖进来的**文件夹会是 `file://` URL**（由 `urls` 给出，`hasUrls` 为真）。Qt 文档没有专门描述 Finder 行为，这条是从 `urls: urllist` 的定义与 macOS 拖放语义推出来的；实现时按 `url.isLocalFile()` + `QFileInfo(path).isDir()` 双条件过滤 `.jianku`。
- ✅ **一个容易漏的坑**：`QQuickDropArea::dropEvent()` 只发 `dropped` 信号，**自己不调用 `accept()`**；而 `QDropEvent` 的构造函数末行是 `ignore()`。所以**不加 `drop.accept()` / `drop.acceptProposedAction()`，放下事件不算被接受**。证据是 Qt 源码：`qquickdroparea.cpp` 的 `QQuickDropArea::dropEvent()` 与 `qtbase/src/gui/kernel/qevent.cpp` 的 `QDropEvent::QDropEvent`（末行 `ignore();`），`acceptProposedAction()` 定义在 `qevent.h`：`{ m_dropAction = m_defaultAction; accept(); }`。（[qquickdroparea.cpp@6.11](https://github.com/qt/qtdeclarative/blob/6.11/src/quick/items/qquickdroparea.cpp)、[qevent.cpp@6.11](https://github.com/qt/qtbase/blob/6.11/src/gui/kernel/qevent.cpp)、[qevent.h@6.11](https://github.com/qt/qtbase/blob/6.11/src/gui/kernel/qevent.h)）
- ✅ `DropArea` 之所以能收到事件，是构造时 `setFlags(ItemAcceptsDrops)`——同 `qquickdroparea.cpp`。所以自己写的接收 item 也要设这个 flag。

#### 从窗口里拖出去 / 撕裂标签 ⚠️ 必须手写

- ✅ QML 侧有 `Drag` 附加属性：`Drag.active`、`Drag.mimeData`、`Drag.hotSpot`、`Drag.supportedActions`、`Drag.proposedAction`、`Drag.imageSource`、`Drag.dragType`（`None` / `Automatic` / `Internal`），方法 `startDrag(supportedActions)` / `drop()` / `cancel()`，信号 `dragStarted()` / **`dragFinished(DropAction)`**——[Drag](https://doc.qt.io/qt-6/qml-qtquick-drag.html)。
- ✅ **Qt 源码确认：`startDrag()` 是阻塞的嵌套 `QDrag::exec()` 事件循环。** `qquickdrag.cpp` 里 `dragType: Automatic` 分支专门把它推迟到队列调用，注释写得很直白：「`QDrag::exec()` enters a nested event loop; calling it directly from a QML binding or JS expression would block the engine mid-evaluation.」（[qquickdrag.cpp@6.11](https://github.com/qt/qtdeclarative/blob/6.11/src/quick/items/qquickdrag.cpp)）
- ❗ **关键限制：Qt 无法告诉你"拖到了应用外面"。** 拖到桌面/别的 app 上，`dragFinished` 收到的是 `Qt.IgnoreAction`，`Drag.target` 是 `null`——**与"用户按了 Esc 取消"完全无法区分**。所以"拖出窗口 → 变成新窗口"不能靠拖放目标驱动，必须自己记录释放点坐标（`dragFinished` 时取 `QCursor::pos()` 或自己跟踪最近一次鼠标位置），然后做几何判断：落点不在任何编辑器窗口的 `frameGeometry()` 内，就在那里开一个新窗口。**这一条要在需求里说清楚，否则实现者会去找一个不存在的 API。**
- ✅ 本仓库已经有"往应用外拖"的现成写法可抄：`MacCapture::beginAppDrag()`（`src/mac/MacCapture.mm`）用 `QMimeData::setUrls` + `QDrag`（父对象取 `QGuiApplication::focusWindow()`）+ `drag->exec(Qt::CopyAction)`。

#### 菜单栏 ⚠️ 需要决策（见第 6 节）

- ✅ Qt Quick Controls 的 `MenuBar` **自 Qt 6.8 起在 macOS 上是原生菜单栏**：「all Menus, MenuItems and MenuBarItems within a MenuBar will also be native… the delegates set on the mentioned controls **will not be used** for rendering. If a native MenuBar is not wanted, you can set `QGuiApplication::setAttribute(Qt::AA_DontUseNativeMenuBar)`」——[MenuBar](https://doc.qt.io/qt-6/qml-qtquick-controls-menubar.html)；`AA_DontUseNativeMenuBar` 的说明见 [Qt Namespace](https://doc.qt.io/qt-6/qt.html#ApplicationAttribute-enum)。
- ✅ 它挂在 `ApplicationWindow.menuBar` 上——[ApplicationWindow](https://doc.qt.io/qt-6/qml-qtquick-controls-applicationwindow.html)。
- ❗ **macOS 的菜单栏是应用级的，不是每窗口一份。** `QMenuBar` 文档：「On macOS … QMenuBar is a wrapper for using the **system-wide** menu bar. If you have **multiple menu bars in one dialog the outermost** menu bar … will be used for the system-wide menu bar.」——[QMenuBar](https://doc.qt.io/qt-6/qmenubar.html)。所以 N 个编辑器窗口共用一份菜单，菜单项的**启用状态与目标必须跟随最前面的那个窗口**。⚠️ 推断：用 QML 的 `ApplicationWindow.menuBar` 在 N 个窗口上会互相争抢，**建议在 C++ 里用 `QMenuBar`/`QMenu`/`QAction` 建一份应用级菜单**，动作路由到 `QGuiApplication::focusWindow()` 对应的会话。
- ⚠️ 一个可行但更土的替代：留一个**永不显示的** `ApplicationWindow` 专门承载 QML `MenuBar`，状态由注册表绑定。我没有实测这条，列在这里仅供比较。

#### 快捷键 ✅ 开箱即用

- `Shortcut { sequences: [...] }` 支持 `StandardKey.New` / `.Save` / `.SaveAs` / `.Close` / `.Undo` / `.Redo` 等。文档明确建议标准键用 `sequences` 而不是 `sequence`：「Given that standard keys can resolve to one shortcut on some platforms, but **multiple shortcuts** on other platforms, we recommend always using `sequences`」——[Shortcut](https://doc.qt.io/qt-6/qml-qtquick-shortcut.html)、[QKeySequence::StandardKey](https://doc.qt.io/qt-6/qkeysequence.html#StandardKey-enum)。
- ✅ `Shortcut.context` 默认 `Qt.WindowShortcut`：「active when its parent item is in an **active top-level window**」——对"⌘S 只作用于当前窗口"正是想要的语义。
- ⚠️ 但**菜单栏快捷键会盖掉同键的 `Shortcut`**。同一个动作只在一处定义，不要两边都写（否则会得到 `activatedAmbiguously` 或干脆不触发）。

#### 其它零碎

- ✅ `QFileSystemWatcher`：可监视文件与目录；目录内容变化发 `directoryChanged`；**不递归**；「if there are several changes during a short period of time, some of the changes **might not emit** this signal」；macOS 用的是另一套后端，不受 BSD 的 256 fd 限制——[QFileSystemWatcher](https://doc.qt.io/qt-6/qfilesystemwatcher.html)。用法：监视 `recordingDirectory`（正好匹配 `RecentProjects::list()` 的非递归扫描）+ 去抖定时器。
- ✅ `QFileOpenEvent`：macOS 上双击 Finder 里的文档、**把文件拖到 Dock 图标**都会送到 `QApplication::instance()`；需要在 `Info.plist` 声明 `CFBundleDocumentTypes` 才会触发——[QFileOpenEvent](https://doc.qt.io/qt-6/qfileopenevent.html)。Screen Studio 的 Info.plist 正是这么做的（`LSTypeIsPackage=true`，本机验证）。**这是最便宜的系统集成**：双击 `.jianku` 直接开一个标签页。
- ✅ `QWindow::setFilePath()` 存在（macOS 上会给出标题栏的代理图标与文档关联）——[QWindow](https://doc.qt.io/qt-6/qwindow.html#setFilePath)。⚠️ `setWindowModified` 是 `QWidget` 上的，`QWindow` 没有；未保存小圆点要自己做。
- ✅ 本工程已经设了 `QGuiApplication::setQuitOnLastWindowClosed(false)`（`main.cpp`），所以关掉最后一个编辑器窗口不会退出——这是对的（有托盘兜底），但意味着 `⌘W` 必须显式处理，否则用户会以为 app 卡住了。
- ✅ 单例是**按引擎**的，且「singleton types **do not have an associated QQmlContext** as they are shared across all contexts in an engine」——[Defining QML Types from C++](https://doc.qt.io/qt-6/qtqml-cppintegration-definetypes.html)。一个引擎 ⇒ 一份 `EditorSessionRegistry`，正好。

## 本项目建议的架构

### 一句话方案

**一个进程、一个 `QQmlEngine`、每个编辑器窗口一个 `QQuickWindow`、每个工程一个 `EditorSession`；会话（不是窗口）持有 `TimelineController` 与 `ExportController`；标签内容只搬视觉父、永不重建；`⌘S` 写工程目录里的编辑旁挂文件。**

### 4.1 会话模型：把每工程状态从根上下文里拿出来

**现状（必须改的地方）**：`main.cpp` 里 `Render::TimelineController timeline;` 与 `Render::ExportController exporter;` 是**全局单例**，通过 `engine.rootContext()->setContextProperty` 暴露；`capture.lastRecordingPathChanged` 把它们指向"刚刚录完的那个工程"。`TimelineController` 里还藏着**唯一的撤销栈**。

这套结构下，标签页在语义上不可能成立：两个标签页会共用一个撤销栈、一个播放头、一个导出目标。

引入三个新类型：

| 类型 | 职责 | QML 可见性 |
|---|---|---|
| **`EditorSession`**（每工程一个） | 持有 `projectDirectory`、加载后的 manifest 事实、`TimelineController`、`ExportController`、编辑旁挂文件路径、`dirty`、以及那个可搬运的 `contentItem` | **注入到该标签页的创建上下文**，不进根上下文 |
| **`EditorSessionRegistry`**（全局唯一，唯一新增的根上下文对象） | `projectDir → session` 映射；`openOrFocus` / `newWindow` / `newTab` / `tearOff` / `closeTab` / `recentlyClosed`；`RecentProjects` 扫描 + `QFileSystemWatcher` 去抖 | 根上下文（建议用 `qmlRegisterSingletonInstance`，让 QML 编译器与工具能看到） |
| **`EditorWindowManager`**（全局唯一） | `QQuickWindow` 台账、窗口↔标签映射、拖出几何、活动窗口/活动会话判定 | 作为 registry 的 `Q_INVOKABLE`，不单独暴露 |

**建议新增文件**（给实现者一个具体的落点）：

```
src/editor/EditorSession.{h,cpp}          每工程状态 + 每工程撤销 + 脏标记 + 保存/加载
src/editor/EditorSessionRegistry.{h,cpp}  唯一的根上下文单例
src/editor/EditorWindowManager.{h,cpp}    窗口台账、标签↔窗口、拖出、目录监视
src/editor/EditSidecar.{h,cpp}            edit.json 的原子读写（照抄 SettingsStore 的 QSaveFile + commit 模式）
ui/EditorWindow.qml                       Window + 标签栏 + DropArea + 空状态
ui/EditorTab.qml                          预览 + 时间线 + 设置栏（被搬运的那个 Item）
ui/TabBarStrip.qml                        自绘标签栏（关闭按钮、中键、脏点、拖动重排）
```

**迁移步子**：先保留旧的全局 `timeline`/`exporter` 作为空壳一版，把 `Main.qml` 改成不再读它们，再删除根上下文里的这两项。避免一次性大爆炸。

### 4.2 打开工程：沿用现有唯一漏斗，但让**主窗口**决定时机

现有链路是干净的：`RecentProjects::list()` 扫目录 → `MacCapture::openProject(path)` 只做一件事：设 `lastProjectPath_` 并 `emit lastRecordingPathChanged()`（`src/mac/MacCapture.mm:1370`）。

建议：

1. **不要**让编辑器去抢 `lastRecordingPathChanged` 这个信号。让 `Main.qml` 在录制保存完成后显式调用 `registry.openProject(capture.lastProjectPath)` —— 由主窗口决定"何时开编辑器"，注册表只负责"开哪个"。
2. `registry.openProject(path, hint)` 的语义：
   - 目录已在某会话中 → **聚焦那个标签页**（v1 不允许同一工程开两份视图，见第 6 节）。
   - 否则创建 `EditorSession`（读 manifest → 建 `TimelineController` → `load()` → 读编辑旁挂 → 建 `ExportController` 并接好线）。
   - `hint` 决定开在哪：**录制结束 → 新窗口**（贴近 Screen Studio 观感）；**用户主动打开 → 最前面那个编辑器窗口的新标签页**。这个默认值要写成设置项。
3. 拖放：编辑器窗口根部的 `DropArea` → `drop.acceptProposedAction()` → 过滤 `.jianku` 目录 → `registry.openProject(path, {asTab: targetWindow})`。空状态窗口本身就是最大的拖放目标（OpenScreen 与 Screen Studio 都有这个空状态）。
4. **双击 Finder 里的 `.jianku`**：`main.cpp` 里子类化 `QApplication` 覆写 `event()` 处理 `QEvent::FileOpen`，加上 `Info.plist` 的 `CFBundleDocumentTypes`（`LSTypeIsPackage=true`，照 Screen Studio 的写法）。成本很低，收益很高。
5. 主窗口那个按钮：`导出成片` → `打开编辑器`，`enabled` 从 `exporter.defaultOutputPath.length > 0` 改成 `capture.lastProjectPath.length > 0`，`onClicked` 调 `registry.openProject(capture.lastProjectPath)`。**导出按钮整体搬进编辑器窗口**（右上角或设置栏底部整宽，见 Screen Studio）。

### 4.3 撤销/重做跨标签页

**结论：撤销栈按会话隔离，菜单/快捷键按"活动窗口"派发。**

- `TimelineController` 的 `undo_`/`redo_` 本来就在控制器里，随会话走即可，**不用新写**。
- 全局 Edit 菜单的两项（撤销/重做）绑定到 `registry.activeSession()`；`enabled` 跟 `canUndo`/`canRedo` 走，目标在 `focusWindowChanged` 时重算。`⌘Z`/`⌘⇧Z` 同理。
- **明确禁止**：全局撤销栈、两个标签页共享一个 `TimelineController`。前者会让"在 A 里撤销把 B 改了"，后者更糟——`TimelineController::load()` 会直接重置整条时间线。
- ⚠️ 一条容易忽略的：切换标签页时**不要把播放头/选中态推进撤销栈**。Screen Studio 的更新日志专门有一条「When removing slices, undoing, redoing - it will adjust playhead to show exact same moment of the source video」，说明参考实现把"播放头跟随撤销"当成刻意的行为，而不是把播放头本身做成可撤销的操作。OpenScreen 也把选中态排除在撤销状态之外。

### 4.4 `⌘S` 到底存什么：**写编辑旁挂文件**

先回答那个尖锐的问题：**现在有没有东西可存？——有，而且正在丢。**

- 现状：`TimelineController::load()` 每次都把 `timeline_` 硬重置成 `Project::EditTimeline::whole(durationMs)`，撤销栈清空（`src/render/TimelineController.cpp:226`）。也就是说切分、变速、裁剪、删除在**重开工程后全部消失**。
- 但模型层早就准备好了：`EditTimeline::toJson()` / `fromJson(object, durationMs, error)` 已经实现并有测试（`tests/EditTimelineTests.cpp`），只是**没有任何调用点**——JSON 从来没有落过盘。
- 而 `docs/双模式产品范围.md`「编辑器细节」已经写明：时间线要能拖动区间边缘、拆分、删除、调整倍率与焦点，撤销重做要覆盖设置与时间线操作。**"编辑不可保存"是产品要求的缺口，不是一个可以省掉的功能。**

**建议**：

1. **写 `edit.json` 到工程目录**，不动 `project.json`。理由：`project.json` 是录制端的清单，`MacCapture` 在录制/收尾过程中会持续改写它（`state` 字段从 `preparing` → `recording` → `processing` → `readyForProcessing`）；编辑器与录制端并发写同一个文件是实打实的损坏风险。旁挂文件同时保住了"原始素材与 `project.json` 不被编辑修改"这条已经写进研究文档的承诺。
2. 内容建议（版本化，便于以后演进）：
   ```json
   {
     "schema": "jianku-edit/1",
     "projectCreatedAt": "2026-10-04T07:30:12.345",   // 与 project.json 的 createdAt 对齐，防止旁挂串工程
     "timeline": { /* EditTimeline::toJson() */ },
     "appearance": { /* 导出实际使用的画布设置快照 */ },
     "playheadMs": 12345,
     "savedAt": "…"
   }
   ```
   `playheadMs` 值得存：Screen Studio 4.0 明确「Projects open where you left off, at the playhead position you saved」。
3. `TimelineController::load()` 增加一步："旁挂存在 → `EditTimeline::fromJson(..., durationMs, &error)`"。已有的校验会拒绝越界/重叠/非正速度；**校验失败时回退到整段身份时间线并报错，而不是让工程打不开**。
4. **脏标记用快照比较**（照抄 OpenScreen 那招，在 C++ 里做）：`dirty = EditTimeline::toJson() != baseline`（baseline 是上次 load/save 时的 JSON）。为什么不能直接用现成的 `edited()`：`edited()` 的语义是「the export would differ from the recording」，只看「是否不是整段实时播放」。仅切分不改变成片，但它是**一个该被撤销、也值得保存的编辑动作**；而且"存过之后再撤销回原样"应该是干净的，`edited()` 说不出来。段数是个位数，序列化比较是 O(小)。
5. 保存时机：`⌘S`、关闭窗口前（三选一对话框选保存）、退出前（`aboutToQuit` / `commitDataRequest`）、以及**周期性自动保存 + 每次编辑后 N 秒去抖**。后两条对应产品文档里"自动保存项目与事件"的要求。写入用原子替换（`QSaveFile` + `commit()`），避免半截文件。
6. `⌘⇧S`（另存为）：**对目录包没有干净语义**。可选方案见第 6 节，我倾向 v1 不做、并在 UI 上不出现，而不是做一个"只另存 edit.json"的半成品。

### 4.5 导出：每会话一个控制器，全局一条队列

- `ExportController` 搬到 `EditorSession` 里，`setProjectDirectory` + `setTimeline` 的接线也搬到 `EditorSession` 的构造函数里。
- **这一步顺手修掉当前最尖锐的一个隐患**：现在 `main.cpp` 里是
  ```cpp
  QObject::connect(&capture, &MacCapture::lastRecordingPathChanged, &exporter, [&]{ exporter.setProjectDirectory(capture.lastProjectPath()); });
  QObject::connect(&timeline, &Render::TimelineController::timelineChanged, &exporter, [&]{ exporter.setTimeline(timeline.timeline()); });
  ```
  全进程只有一个 exporter，它指向"最后被打开的那个工程"。有了多标签页，用户在 A 里点了导出、又切到 B，导出目标与时间线就可能对不上。按会话持有就自然没这个问题。
- 多标签页会带来**多个 ffmpeg 流水线抢机器**的必然问题（每个 `ExportController` 自带一个工作 `QThread`，`composeProject()` 同步驱动两个 ffmpeg 进程）。建议：**全局串行队列**，同一时刻只跑一个导出，其余显示"排队中"；标签在后台时用角标/小圆点显示进度。

### 4.6 关闭与退出

- 拦截窗口 `closeEvent`（QML `onClosing` 或 C++ 事件过滤器）→ 若该窗口里**有脏会话**，用 `MessageDialog`（**显式设 `parentWindow`**）问保存/不保存/取消 → 只在最后一个标签页关闭时才关窗口。
- 保持 `quitOnLastWindowClosed(false)`；托盘是回来的路。现有 `main.cpp` 已经这么做了。
- 托盘/菜单里的 `打开简库镜传` 应该聚焦或新建编辑器窗口，而不是主窗口。⚠️ 需要确认产品意图（主窗口还承担录制职责，见第 6 节）。

### 4.7 菜单与快捷键

建议在 C++ 建一份**应用级**原生菜单（理由见 3.3），动作路由到 `registry.activeSession()`：

| 菜单项 | 快捷键 | 行为 |
|---|---|---|
| 新建编辑器窗口 | `⌘N` | `registry.newWindow()`（空窗口，显示空状态） |
| 打开工程… | `⌘O` | `FolderDialog` → `registry.openProject(path, asTab: activeWindow)` |
| 打开最近的 | 子菜单 | `RecentProjects::list()`，比 OpenScreen 的单一 `projectDirectory` 记忆更完整 |
| 保存 | `⌘S` | 活动会话写 `edit.json` |
| 关闭标签页 | `⌘W` | 关标签页；最后一个标签页则关窗口（脏则先问） |
| 导出成片 | `⌘E` | 活动会话发起导出（需用户确认键位） |
| 撤销 / 重做 | `⌘Z` / `⌘⇧Z` | 活动会话 |
| 下一个 / 上一个标签页 | `⌘⇧]` / `⌘⇧[` | 窗口内 |
| 重新打开关闭的标签页 | `⌘⇧T` | `registry.reopenLastClosed()` |
| 工程 → 在 Finder 中显示 / 复制路径 | | `⌘` 系列 |

`⌘N` 的语义需要定：Screen Studio / OpenScreen 的 `⌘N` 是**新工程**。我们没"从零建工程"这个概念（工程 = 一次录制），所以建议 `⌘N` = 新编辑器窗口（空状态，可拖工程进去或直接开始录制）。见第 6 节。

### 4.8 其它"用户期待但没明说"的affordance（用户点名要我想的）

按重要性排序：

1. **关闭按钮**：悬停时显示在标签上；脏标签常驻一个圆点；中键关闭；`⌘W` 关闭当前标签。
2. **窗口标题显示当前标签名 + 脏标记**；`QWindow::setFilePath()` 让 macOS 显示代理图标与文档路径（`setWindowModified` 在 `QWindow` 上不存在，脏点要自己画）。
3. **重新打开刚关掉的标签**（`⌘⇧T`）——需要注册表维护一个小的"最近关闭"栈（路径 + 原窗口 + 原位置）。
4. **标签右键菜单**：关闭 / 关闭其他 / 关闭右侧 / 在 Finder 中显示 / 复制工程路径 / 在新窗口中打开 / 重新载入。
5. **标签拖动重排**，带插入位置指示线；要有拖动阈值，否则一次点击就会被当成拖动。
6. **拖出成窗**：在新窗口落点处建窗（沿用原窗口尺寸）；如果源窗口因此空了，关掉它。
7. **启动恢复**：记住打开的工程路径 + 每个窗口的位置尺寸，下次启动恢复。⚠️ 恢复时不要触发"自动打开编辑器"，否则会跟主窗口的录制流程打架。
8. **最近工程列表**：主窗口 + 编辑器 `File → Open Recent` + （可选）Dock 菜单。`RecentProjects` 已经能提供数据。
9. **空状态**：拖放区 + 「打开工程…」+「开始新录制」。这是让拖放可被发现的关键。
10. **后台标签的进度可见**：正在导出的标签要有角标/圆点，否则用户会以为导出没了。
11. **多显示器/全屏**：拖出成窗时应落在鼠标所在的那块屏幕（`QWindow::setScreen`）。
12. **`⌘1..9` 切换标签**、`⌘\`` 在窗口间切换（后者靠 macOS 的 Window 菜单 role 基本免费）。

**v1 明确不做**：同一工程多视图、标签分组、垂直标签、标签动画、`QQuickRenderControl` 离屏渲染。

## 一期功能清单

按价值排序，每条一句理由。

1. **`EditorSession` + `EditorSessionRegistry`**：把每工程状态从根上下文拆出来——在一个全局 `TimelineController` 之上盖任何东西都会在第二个标签页出现时崩掉。
2. **编辑器做成独立的 `QQuickWindow`（同一个引擎），录制结束后打开**：这是用户的原话，也是让主窗口不再既当录制器又当编辑器的前提。
3. **主窗口 `导出成片` → `打开编辑器`；`打开工程…` 用原生 `FolderDialog`**：让后续所有能力有一个入口，且这是本仓库已有的 `RecentProjects` / `openProject` 的自然归宿。
4. **标签内容做成"只搬视觉父、永不重建"的 Item（先写探针验证）**：整份方案里风险最高的假设，值得在写任何 UI 之前先在真机上证伪一次。
5. **单窗口编辑器跑通**：预览（由会话提供帧源）+ 把 `TimelineStrip` 搬进标签内 + 右侧设置栏（背景/留白/圆角/内缩/阴影）+ 每会话 `ExportController` + 导出按钮。没有这些，标签页只是装饰。
6. **C++ 应用级原生菜单，作用域跟随最前窗口（`⌘N/O/S/W/E`、撤销重做）**：macOS 上菜单是全局的，用 QML 每窗口一份必然打架；同时 `⌘S` 才第一次有真正的目标。
7. **`edit.json` 旁挂读写 + 脏标记 + 关闭确认**：把"非破坏性时间线"从"重开就没了"变成真正的文档，这才让 `⌘S` 诚实。
8. **把 `.jianku` 目录拖进编辑器窗口 → 作为新标签页打开**（`DropArea` + `drop.urls` + 显式 `accept`），含空状态拖放区：用户明确要求，且在 (3) 完成后成本很低。
9. **标签基本操作**：关闭按钮、中键关闭、`⌘W`、脏点、右键菜单（关闭其他/右侧）：这些是用户默认存在的能力，缺一个都会被当成 bug。
10. **标签拖动重排 + 拖出成窗**：用户明确要求；放在 (9) 之后，因为 Qt 没有"拖到应用外"的事件，必须自己做释放点几何判定，最容易出错。
11. **重新打开关闭的标签（`⌘⇧T`）+ 启动恢复（工程路径 + 窗口位置）**：两个"只有缺失时才会被注意到"的常规编辑器能力。
12. **`QFileOpenEvent` + `Info.plist` 的 `CFBundleDocumentTypes`/`LSTypeIsPackage`**：双击 Finder 里的工程直接开标签页，是成本最低的系统集成。
13. **导出串行队列 + 后台标签进度角标**：一旦有标签页，两个 ffmpeg 抢机器是必然事件，不是可能事件。
14. **自动保存（退出时 + 周期）与旁挂损坏时的降级提示**：产品文档已经承诺"自动保存项目与事件"，不能只做手动保存。

## 不确定/需用户确认的点

1. **Screen Studio 没有标签页**（我没找到任何证据；证据只支持"多窗口 + 一窗一工程"）。所以标签、拖出成窗是我们的**新增能力**，验收标准要自己定，不能拿"和参考一致"当挡箭牌。
2. **"拖出窗口"的判定边界**：Qt 在拖到桌面/其他 app 时只会给 `Qt.IgnoreAction`，与按 Esc 取消不可区分。要不要接受"拖到屏幕空白处也成窗"这种近似？还是要求"必须落在某个编辑器窗口之外、且不在菜单栏/Dock 上"？
3. **录制结束后开新窗口还是加新标签页？** 我的建议：录完开**新窗口**（贴近参考观感），用户主动"打开工程"则加**标签页**。需要拍板，并决定要不要做成设置项。
4. **同一个 `.jianku` 被拖两次**：聚焦已有标签页，还是允许同一工程开两个视图？我建议前者（v1）。
5. **`⌘⇧S`（另存为）对目录包意味着什么？** 只复制 `edit.json`？整体复制 `.jianku`（含可能几 GB 的 `raw.mp4`）？还是 v1 不做？**这条必须由用户定**，我不建议擅自实现。
6. **`edit.json` 这个文件名与结构是否接受。** 它会成为工程目录里的对外契约（第 4.4 节给了草案）。另外需要确认录制端的收尾流程（`MacCapture` 的 `finalizing`/`processing`）**不会清理它不认识的文件**——如果会，得先改录制端。
7. **关闭时的三选一对话框用原生还是自绘。** 原生更像 Mac，但 N 个窗口下 `parentWindow` 必须显式绑定；自绘可控但要自己处理模态。
8. **要不要把菜单从 QML 搬到 C++。** macOS 菜单栏是应用级的，多窗口下必须共享一份并跟随最前窗口。我建议搬到 C++ 的 `QMenuBar`，但这是一次额外重构。
9. **允不允许两个标签页同时导出？** 我建议全局串行队列（CPU/磁盘 + 输出路径本来就按工程隔离）。
10. **每个标签页的播放头与时间线缩放位置是否随工程保存？** 参考实现明确保存播放头。这要在 v1 就把 `playheadMs`（与可能的 timeline zoom）写进 `edit.json` 的数据契约里。
11. **`⌘N` 的语义**：我们没有"从零建工程"，所以建议 `⌘N` = 新建空编辑器窗口。需要确认。
12. **主窗口的定位**：搬走编辑器后，主窗口只剩"选源 + 录制 + 演示 + 快捷截图"。托盘/菜单里的"打开简库镜传"应该打开主窗口还是编辑器窗口？录制结束后主窗口要不要留着？
13. **实机验证缺口**：我的跨窗口搬运探针跑在 `QT_QPA_PLATFORM=offscreen`（无头）上。真机上的窗口层叠、`transientParent`、拖放语义、多屏落点、以及"拖出时窗口是否跟随鼠标"都还没验证。**建议第一步就是在真机上把这个探针跑一遍**，源码见附录 A。
14. **版本证据的不一致**：Screen Studio 部分混合了三套证据——官网指南（当前版，4.0 时期）、官网 changelog、本机 `/Applications` 里的 **3.4.4-3794** asar 静态分析、以及 `research/evidence/` 里的 **3.7.5** 签名包。凡是引用具体版本行为的结论，都标了版本号；`ChildWindow` 机制确实存在，但我**没有**验证它（在 3.4.4 里）就是编辑器标签/子窗口系统。

`main.cpp`（探针对象，只做观测与搬运）：

```cpp
class Probe : public QObject {
    Q_OBJECT
public:
    using QObject::QObject;
    Q_INVOKABLE void dump(QQuickItem *item, const QString &label) {
        if (!item) { qInfo().noquote() << label << "item=null (DANGLING)"; return; }
        QQuickWindow *w = item->window();
        qInfo().noquote() << label
            << "| window:"    << (w ? w->title() : QStringLiteral("<null>"))
            << "| parentItem:"<< (item->parentItem() ? item->parentItem()->objectName() : QStringLiteral("<null>"))
            << "| qobjectParent:" << (item->parent() ? item->parent()->objectName() : QStringLiteral("<null>"))
            << "| visible:"   << item->isVisible()
            << "| tick:"      << item->property("tick").toInt();
    }
    Q_INVOKABLE void moveTo(QQuickItem *item, QQuickItem *host) { if (item && host) item->setParentItem(host); }
    Q_INVOKABLE void detach(QQuickItem *item) { if (item) item->setParentItem(nullptr); }
    Q_INVOKABLE void watch(QObject *o) { g_owned = o; }
    Q_INVOKABLE void watchStatus(const QString &label) {
        qInfo().noquote() << label << "watched object:" << (g_owned.isNull() ? "DELETED" : "alive");
    }
};
```

`Main.qml`（关键部分：QObject 父决定生死；视觉父可跨窗口搬）：

```qml
Item {
    id: root
    property int ticks: 0
    Timer { interval: 100; running: true; repeat: true; onTriggered: root.ticks++ }

    // 用例 A：QObject 父是窗口本身 —— 窗口关闭后 item 被销毁
    Window {
        id: winA
        title: "A"; width: 420; height: 300; visible: true
        Item { id: hostA; objectName: "hostA"; anchors.fill: parent
               TabContent { id: ownedByA; objectName: "ownedByWindow"; tick: root.ticks } }
    }
    // 用例 B：QObject 父是 root —— 跨窗口搬运后仍然活着
    TabContent { id: detachedOwner; objectName: "ownedByRoot"; tick: root.ticks }

    Component.onCompleted: {
        probe.watch(ownedByA);  probe.dump(ownedByA, "A1 QObject-父=窗口")
        probe.dump(detachedOwner, "B1 QObject-父=root")
        probe.moveTo(detachedOwner, hostA);  probe.dump(detachedOwner, "B2 挂进 hostA")
        // ... 之后 setParentItem(nullptr) / 挂到另一个窗口 / close(winA) 再观察
    }
}
```

`QQuickWindow` 的 `acceptDrops` 细节：`QQuickWindow` **没有**公开的 `acceptDrops()` 访问器（我在探针里试过，编译失败），命中测试是 Qt 内部在投递拖放事件时做的——只要场景里有 `ItemAcceptsDrops` 的 item 且拖放坐标落在它上面，`DropArea` 就会收到事件，不需要动窗口标志。
