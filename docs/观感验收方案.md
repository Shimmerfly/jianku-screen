# 观感验收方案

日期：2026-10-04｜状态：方案已定，第 0 轮（可测部分）已跑

「观感」这个词很容易变成一句「我觉得不太对」。这个文件把它拆成**可以判定的问题**，
每一条都写清楚：拿什么比、比哪个数、多少算过。

---

## 一、先说清楚哪些能自动判、哪些不能

| 类别 | 例子 | 怎么判 |
|---|---|---|
| **可测量** | 视差、缩放倍率、时序、帧率、圆角像素、留白比例 | 脚本判，有数值门槛 |
| **可对齐** | 指针轨迹、镜头起止时刻、模糊方向 | 与参考逐帧相关性比对 |
| **只能人看** | 「顺不顺」「自不自然」 | 人看 A/B 对照，但**必须同时给可测指标**，否则改完不知道是变好还是变坏 |

我的做法是：**能用数字表达的绝不用形容词**，剩下真正只能人看的部分，
做成一份固定的对照清单，每次改动后跑同一份，避免「这次感觉比上次好」。

## 二、参照物是什么

这是整套验收的地基，先定死：

1. **参考软件的记录**：`~/Screen Studio Projects/` 里有 6 个 `.screenstudio` 工程，
   **只读**。它们是唯一能告诉我们「参考到底怎么动」的东西——每个工程里
   `project.json` 记录了 `zoomRanges`（含 `zoom` 倍率、`snapToEdgesRatio`、
   `startTime`/`endTime`、`type`），实测样本：

   ```
   一个 2 分钟的录制里有 9 段自动缩放，zoom 全是 1.459，
   snapToEdgesRatio 全是 0.25，type 全是 follow-click-groups
   ```

   这几条**直接可验收**：我们的自动缩放产出的区间，倍率是否也是 1.459、
   区间起止是否与它的 click group 分组一致。

2. **我们自己的真机录制**：`~/Movies/Jianku Screen/...22-46-50-891.jianku`
   （3360×2100、6830 帧、1532 个指针事件、6 种光标、4 段缩放、124.66 秒）。
   改代码前后都跑同一条命令导出同一段，逐帧比。

3. **不拿它当参照的东西**：OpenScreen 的动画曲线（用户明确说太烂）。

## 三、可自动判定的部分

### 3.1 画布外观：与导出**逐像素相等**

最硬的一条，已经能跑：

```sh
# 用参考工程的设置导出 30 帧，与「预览的排版参数」比对
./build/jianku-compose --frames 30 --no-audio -o /tmp/check.mp4 <工程>
```

判定：预览的 `radiusRatio × 画布高` 必须**等于**导出画面里的圆角像素数（误差 ≤1 px）。
这条今天刚发现过一次失败：预览按「点」排版、导出按「像素」排版，
Retina 上圆角差了**整整 2 倍**——正是用户看到的「预览圆角比成片大很多」。
现在 `canvas-renderer-tests` 把「像素排版的圆角比例与导出完全相等」
和「按点排版会得到 2.0x」两条都写成了断言。

### 3.2 自动缩放：与参考工程的 `zoomRanges` 对齐

```sh
python3 - <<'PY'
import json, os
D = os.path.expanduser("~/Screen Studio Projects/Built-in Retina Display 2026-09-19 10:30:23.screenstudio")
ranges = json.load(open(D + "/project.json"))["json"]["scenes"][0]["zoomRanges"]
for r in ranges:
    print(f'{r["startTime"]:>7} .. {r["endTime"]:>7}  zoom={r["zoom"]}  snap={r["snapToEdgesRatio"]}')
PY
```

判定三件事：
1. **倍率**：参考固定 1.459，我们的默认值是否落在同一数量级？
2. **边界**：区间起点是否等于那次点击的时刻（我们的 `automatic-zooms.json` 同样是
   可读的，直接比时间）；
3. **数量**：同一段录制里，我们分出的区间数是否与参考同量级
   （参考是 2 分钟 9 段；如果我们是 3 段或 30 段，一定是分组规则不同）。

**第 0 轮已跑，结果如下。** 参考工程与我们的录制内容不同，所以比的是统计特征，
不是具体时刻。

参考的 6 个工程共 **39 段缩放区间**，全字段一致得可怕：

| 字段 | 取值 | 段数 |
|---|---|---|
| `zoom` | **1.236 或 1.459** | 8 / 31 |
| `type` | `follow-click-groups` | 39 / 39 |
| `snapToEdgesRatio` | `0.25` | 39 / 39 |
| `hasInstantAnimation` | `false` | 39 / 39 |

**我们的默认值是 2.0**（`src/animation/AutoZoomEngine.h:29` 与
`AutomaticZoom.h:7` 的 `zoom = 2`）。也就是说我们的自动缩放**比参考猛得多**：
参考最多放大到 1.459 倍，我们是 2 倍，画面里对象的尺寸差了 37%。

第二项：区间时长。参考中位 **7.5 秒**（1.6–34.5 秒）；
我们的单次点击区间是 `−300 ms … +2500 ms`，即 **2.8 秒**，
靠合并才能变长。参考的中位数是我们单段长度的 2.7 倍。

`zoom` 只有两个取值，说明它**不是**按内容算出来的，而是一个工程级的档位。
两个值与 `cameraScaleDuringZoom = 0.7` 都对不上（1/0.7 = 1.429），
也不随 `backgroundPaddingRatio`、`windowBorderRadius` 变化。
**它从哪来还没确定**——`app.asar` 里的主进程包是混淆过的，
静态找常数没有结果。下一步要么动态观察（改一次缩放档位再看
`project.json` 怎么变），要么就当作「两档预设」照抄 1.236 / 1.459。

**区间起止的 lead**：参考里「区间起点 = 区间内首次点击 − 中位 1627 ms」。
但这条**证据不干净**——39 段里有 15 段区间内一次点击都没有，
说明区间是分组产生的结果、而我的分组复现不对，所以这个中位数被污染了，
**不作为结论**。它需要先把参考的分组规则复现出来才能量。

### 3.3 指针轨迹：与参考逐帧相关性

已有的做法（`research/指针链路-核对.md` 里记录过）：把参考成片与我们导出的同一段
解码成帧，对每一帧求指针区域的质心，比较两条轨迹的**延迟**与**超调量**。

判定：
- **延迟**：参考在点击后多少毫秒到达稳定位置，我们是否在 ±1 帧内；
- **超调**：峰值是否越过目标位置、越过多少（弹簧欠阻尼的特征；
  参考默认 470/70/3 是**过阻尼**，几乎不超调——这条本身就是可判定的）；
- **轨迹相似度**：归一化互相关 > 0.98 算过。

### 3.4 动态模糊：方向、强度、通道

已实现的做法（`research/画布与运动模糊.md`）：
- 通道由**中心位移 vs 尺寸变化**决定；
- 强度 × fps/60；
- 移动核 21 抽头单边；缩放核 13 抽头，权重 `4(p − p²)`；
- 父层运动扣除。

判定：对已知的一段纯平移，导出帧的模糊方向必须与运动方向一致（角度误差 < 5°）；
对一段纯缩放，模糊必须是径向的。这两条都可以用相邻帧的差分成像自动判。

### 3.5 时序与帧率

- 导出的帧数必须等于 `时长 × fps`（±1 帧）；
- 暂停折叠后，音画偏移 < 1 帧（已用 `--microphone-volume` 的实测方法验证过音量，
  同一条链路上可以量偏移）。

## 四、只能人看的部分（固定清单，每次同一份）

做成一段**固定的操作脚本**，每次改动后录一遍、导出、看同样几个时刻：

| # | 看什么 | 具体问题 |
|---|---|---|
| 1 | 指针启动 | 从静止开始移动时，是「弹出去」还是「滑出去」？有没有一顿一顿 |
| 2 | 指针停止 | 停下时有没有肉眼可见的过冲（超出再回来） |
| 3 | 点击反馈 | 点击瞬间的缩小是否有弹性，还是一下子跳小 |
| 4 | 缩放进入 | 画面开始放大到稳定，大约多久？有没有「先快后慢再快」 |
| 5 | 缩放跟随 | 放大状态下移动指针，画面是否平滑跟随，还是会甩 |
| 6 | 缩放退出 | 回到全景时是否回到**原来的位置**（不回位是最常见的问题） |
| 7 | 拖拽 | 拖动窗口/滑块时，弹簧是否明显变硬（参考的拖拽档 1000/40/1） |
| 8 | 光标形状切换 | 从箭头到文本光标，形状切换是否突变 |
| 9 | 边缘 | 指针到屏幕边缘时，缩放是否贴边停住（`snapToEdgesRatio`） |
| 10 | 动态模糊 | 快速移动时是否「轻微」——糊过头比不糊更糟 |

每一项打 1–5 分，与上一次的分数对比。**分数本身不重要，
重要的是「同一个问题在不同版本之间的变化方向」。**

## 五、这轮已经验掉的与还没验的

**已验**（有断言或实测数据）：
- 画布比例：16:10 的源导出 1080p 得 1728×1080，不是 1920×1080（有测试）；
- 预览与导出的圆角比例**完全相等**（有测试，且把「按点排版 = 2.0x」写进去了）；
- 指针坐标的像素/点两个空间互不串（有测试）；
- 时间线编辑在重开应用后还在（有测试）。

**未验**：3.2 的区间统计特征、3.3 的轨迹相关性、3.4 的模糊方向自动判定、
第四节整张人看清单。**这些都还没跑过第一轮**，所以现在的「观感」是未验收状态。

**下一步**：先把 3.2 跑出来——它不需要人看，也不需要人工标注，
只要把参考工程的区间统计与我们的并列打印。这一步能立刻回答
「我们的自动缩放是不是比参考早/晚/多/少」。
